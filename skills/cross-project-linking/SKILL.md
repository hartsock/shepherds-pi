# Shepherd cross-project linking

You choose the system boundary and inspect pi's result. Every property must
remain a complete entry point, even when a reader starts there directly.

For helper assignment, isolation, dispatch, integration, and blocked-state
handling, follow the [shared shepherd loop](../../docs/shepherding.md).

## Brief the helper

Give pi the canonical properties, owned files, preserved content, visibility
constraints, and the exact commands and evidence required for acceptance.

> Add or repair the ecosystem navigation within the assigned files.
> Define one ordered link set as data and import it in every renderer and test.
> Render every property on every leg, including a marked `You are here` row.
> Keep labels, roles, and canonical URLs identical across outputs.
> Add a fetch-based check for the full directed-link matrix.
> Return the diff, commands, results, and access limitations. Do not delegate.

## Inspect and accept

- Count `N × (N - 1)` directed cross-property links.
- Confirm every block contains all `N` rows, including its current row.
- Trace labels, roles, and URLs to one canonical data definition.
- Inspect imports; reject copied generator or test allowlists.
- Fetch each reader-facing property and assert every canonical URL appears.
- Check restricted links using each intended audience's access level.

Reject partial linking. A property that receives links but provides no return
path remains orphaned. Reject visual assurance without fetch-based evidence.
Link presence neither grants access nor proves that ordinary readers avoid a `404`.

Consult the [cross-project linking doctrine](../../docs/cross-project-linking-doctrine.md)
for the graph rule, data boundary, failure example, and acceptance matrix.
